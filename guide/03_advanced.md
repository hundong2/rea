## Evidence를 주장 단위로 읽기

실습에서 `normalized_result`는 결과 데이터, `subject`는 대상, `parameters`는 요청 선택, `provider`는 분석기 식별, `limitations`는 남은 한계다. Evidence ID는 canonical 내용에 기반한 식별값이며 사실의 완전성이나 사용자의 결론이 옳다는 인증서가 아니다.

| 확인할 주장                   | 사용할 근거                           | 아직 알 수 없는 것                         |
| ----------------------------- | ------------------------------------- | ------------------------------------------ |
| preload에 공개 API가 있다     | context bridge 관찰·소스 위치         | 앱 실행 중 그 코드가 도달 가능한가         |
| IPC 채널 송신·처리가 대응한다 | literal channel·송신·handler 관계     | 실제 요청이 성공했는가                     |
| artifact 내용이 식별됐다      | root artifact SHA-256·inventory 정보  | 동적으로 내려받는 코드가 있는가            |
| 특정 소스를 선택했다          | source_selection.requested_paths      | 선택하지 않은 의존 파일의 의미             |
| 그래프에 관계가 없다          | coverage·unknown·limitations부터 확인 | 실제로 관계가 없는가, 분석에서 못 찾았는가 |

## 선택 범위를 좁혀 보기

세 번째 실습은 전체 inventory를 유지하면서 `preload.cjs` 한 파일만 분석한다. `unselected_files=5`는 다른 파일이 없다는 뜻이 아니다. root identity와 소스 분석 coverage가 함께 남아야 결과를 다시 해석할 수 있다.

추가 과제는 preload와 main을 차례로 선택하고 `requested_paths` 순서와 IPC summary를 비교하는 것이다. 변경 전후 Evidence, 입력과 한계를 함께 보관한다. 텍스트 결과가 짧아졌다는 이유만으로 토큰·실행 시간·메모리가 모두 개선됐다고 주장하지 않는다.

## 동적 표현을 미확인으로 남기기

fixture에서 `'notes:search'`를 입력에 따라 계산하도록 바꿔 본다. 정적 도구가 분석할 수 없는 경우 channel과 관계를 임의로 복원하지 않는다. API alias 재대입, 동적 import, 난독화, 런타임 등록과 실제 실행은 서로 다른 불확실성이다.

정적 결과를 바탕으로 런타임 관찰을 제안할 수는 있지만 자동으로 프로세스에 연결하는 단계와 같지 않다. 실제 대상을 선택하고 실행·연결 효과, 정리·중단 수명을 확인해야 한다. 본 가이드는 그 확장을 실행하지 않았다.

## 자원 수명으로 실패 분석하기

파일을 읽었다는 사실, 소유권을 증명했다는 사실, 읽은 내용이 유효하다는 사실, 자원을 정리했다는 사실은 다르다. 자원이 닫히지 않았는데 성공 결과만 반환하면 다음 요청의 상태가 불명확해진다.

소스의 `ArtifactResourceScope`와 CLI 어댑터에서 다음 질문을 추적한다.

1. 어떤 객체가 reader·worker를 소유하는가?
2. analysis가 끝나기 전에 reader를 닫는 이유는 무엇인가?
3. 취소가 결과 동결·해시 중에 도착하면 무엇을 남기는가?
4. 분석 실패와 cleanup 실패가 동시에 생기면 어느 정보가 사라지지 않아야 하는가?
5. 부모 프로세스 종료 뒤 worker가 남지 않는다는 근거는 무엇인가?

이 질문의 코드 경로를 읽은 것과 실제 Windows·Linux의 모든 수명 회귀를 실행한 것은 구분한다. 원본 [테스트 안내](../docs/testing.md#lifecycle-regressions)의 lane을 보고 해당 변경에 필요한 실제 provider 검사 범위를 정한다.

## 기여·평가 과제

새 기능을 더하기 전에 필요한 입력 선택과 결과 계약을 정하고, CLI/MCP 양쪽이 같은 뜻으로 표현하는지 확인한다. 관련 소스 테스트, public boundary 검사, 실제 provider 검증은 다른 증거다. Mock 제공자는 실제 엔진의 정상 동작 증거가 아니다.

이 학습 자료의 출발점은 공개 CLI와 자작 소스다. 이후에는 소유한 작은 앱의 정적 분석, 명확히 한정한 런타임 관찰, 지원 제공자 비교 순서로 진행하되, 각 단계의 확인한 사실·도출·추론·미확인을 따로 기록한다.
